1. Project Overview & Goals
Ascendance Strategies is launching a subscription intelligence platform for the US-DRC Strategic Partnership, critical minerals, and the Sakania-Lobito Corridor. The platform serves a niche audience of institutional subscribers: government bodies, investors, multilaterals, and corporates active in the region.
Phase 1 ships a complete production-ready WordPress platform with: a public marketing site, a gated subscriber product (Briefs, Updates, Dossiers across three access tiers), an AI-assisted editorial workflow so the team can draft long-form content with Claude / GPT / Gemini and humanise before publish, a custom 'Mission Control' admin dashboard showing everything in one place, and the SEO/AEO/GEO foundations to be cited by AI search engines.
1.1 Why this project, in one paragraph
Ascendance's competitors (Africa Intelligence, Africa Confidential, Energy Intelligence) offer breadth. Ascendance's differentiation is single-country depth on the US-DRC Partnership and a distinctive analytical framework (the Strategic Asset Reserve). The platform's job is to monetise that depth through a tiered subscription model, while using AI to accelerate publishing cadence without diluting editorial quality. The platform is the firm's primary revenue engine and primary brand asset.
1.2 The three user types
Public visitor
Reads free public Briefs and the editorial section. Hits a paywall on gated Briefs and Dossiers — sees the headline, dek, analytical claim, public excerpt; the rest requires subscription. Newsletter signup converts them to leads.
Subscriber
Authenticated, paid via Stripe. Three tiers: Essential, Professional, Enterprise. Tier-specific content access. Receives weekly digest and per-category notifications based on preferences they set in their account.
Editorial / admin
Logs in to the Ascendance backend. Sees the Mission Control dashboard. Drafts new content via the AI Studio (Claude/GPT/Gemini-assisted), reviews and humanises, sets tier access, publishes. Sees subscriber stats, AI usage, recent activity in one place.
1.3 The four success criteria
Editor can publish a Brief end-to-end (including AI assist) in under 30 minutes from blank page to live URL.
A new subscriber can complete signup → checkout → first read in under 90 seconds from landing on the subscribe page.
Every published Brief renders correct Article + AnalysisNewsArticle JSON-LD, validated in Google Rich Results Test on first publish.
Mission Control dashboard loads in under 2 seconds and shows: subscriber count by tier, drafts pending review, AI tokens used this month, latest 5 publishes, security/backup status.

Honest scope note
Phase 1 as defined here is a more ambitious build than a 'simple WordPress install with a paywall plugin'. Adding the AI workflow, the Mission Control dashboard, and the custom paywall (instead of a Pro membership plugin) means real engineering work. Plan the timeline as approximately 10–14 weeks end to end, not 4–5. This document deliberately does not put a price on it; that conversation sits with the client separately.

2. The Architecture Decision — Build vs Buy
This project deliberately favours building over buying Pro plugins. The reasoning matters because it shapes everything else in this document.
2.1 The reasoning
Three forces push us toward custom over Pro plugins:
AI tools have changed the build economics. A skilled developer using Claude Code, Cursor, or similar can now build a custom WordPress plugin module in 1–2 days that would have taken 1–2 weeks five years ago. The 'buy' option used to win automatically on engineering cost. That advantage has shrunk.
Pro plugins carry recurring cost forever. Rank Math Pro, SearchWP, WP Rocket, PMPro add-ons, ACF Pro — each is a subscription that renews. Across 5 years, custom code wins cleanly on total cost.
Custom code is portable. If Phase 3 migrates the platform to Next.js + Airtable (the original brief's architecture), the custom plugin's data model and API surface translate cleanly. Pro plugins do not.
2.2 What we BUY (free or genuinely worth it)
We use existing plugins where they do something we cannot reasonably rebuild — security scanning, image format conversion, GDPR compliance, multilingual — and where they're free or pay back their cost many times over.

2.3 What we BUILD (the custom Ascendance Intelligence plugin)
Everything Ascendance-specific lives in one custom WordPress plugin. Plugin slug: ascendance-intelligence. Path: /wp-content/plugins/ascendance-intelligence/. This is the strategic asset of the build — when Phase 2+ work begins, this is the foundation.
The plugin is organised as modules, each in its own subdirectory. Each module is genuinely independent and can be developed/tested in isolation.

2.4 Things that 'sound cheaper to buy' but we still build
Membership/paywall. PMPro is the obvious off-the-shelf. Reason we still build: the paywall is the most-customised surface (branding, AEO/SEO schema, tier-gating logic, preference center, notifications). Building it costs less than configuring + patching PMPro for our specific needs.
SEO schema for AnalysisNewsArticle and FAQPage. Rank Math Pro does these. Building 200 lines of PHP outputs cleaner schema we fully control. Yoast Free handles the basics.
Search. SearchWP is the obvious. Building a weighted WP_Query with 1–2 days of dev work matches 80% of SearchWP for free.
Caching. WP Rocket is excellent but paid. W3 Total Cache (free) covers everything we actually use.
2.5 Things that look 'free' but cost us
Free plugins with paid upsells. Elementor, WP Forms Lite, Optin plugins — most try to upsell every feature you actually need. We avoid the entire category.
Plugins that load on every page even when unused. Slow site, sketchy code. We audit any free plugin before installing.
Plugins maintained by single individuals with low activity. Security risk. We check last-updated dates and active install counts before adopting.
Developer guidance
Use AI coding tools (Claude Code, Cursor, Copilot) aggressively during the custom plugin build. This document is designed to be readable by an AI assistant: you can paste sections directly into Claude Code as the spec, and it will produce starter code. That's the intended workflow.

3.2 Frontend
Custom WordPress theme — NOT Elementor for any subscriber-facing surface.
Block editor (Gutenberg) for editorial content.
Vanilla JS + a small amount of Alpine.js for interactive components (paywall reveal animations, search dropdown, preference toggles). No React for the WordPress frontend — keeps bundle size minimal.
Tailwind CSS for the custom theme, output to a built CSS file. No runtime Tailwind.
Brand tokens as CSS custom properties in a single theme.css file. Theme variants by overriding token values, not rewriting components.
3.3 Backend / plugin
PHP 8.2, strict types, PSR-12 coding standards.
Namespaced classes: Ascendance\Intelligence\Module — no global functions.
Composer for dependencies (Stripe SDK, Brevo SDK, anthropic-sdk-php if used, otherwise direct cURL/Guzzle).
PSR-4 autoloading via Composer.
Custom database tables for ai_drafts, ai_usage_log, paywall_views, preferences. WordPress's wp_options is wrong for these — too volatile, too small.
Migrations on plugin activation via dbDelta.
3.4 Dev tooling
Local: Local by Flywheel, DevKinsta, or LocalWP. Whichever the dev prefers. Docker also fine.
Version control: Git. GitHub or GitLab. Private repository.
Branching: main (production), staging, feature/* branches. PRs reviewed before merge to staging.
Deploys: SSH + git pull to staging and production. WP-CLI for post-deploy steps (cache flush, dbDelta).
AI coding assistants (Claude Code, Cursor, Copilot) — strongly recommended. Speed up the custom plugin build by 3–5×.
Testing: Pest or PHPUnit for plugin logic. Manual QA against the checklists in Section 22.

4.3 What goes in git, what doesn't
In git: the custom plugin, the custom theme, deployment scripts, this documentation, the wp-config-sample.php (with placeholders, NO real keys).
Not in git: wp-config.php (real keys), .env (real secrets), /wp-content/uploads/ (images — too large, sync separately), /wp-content/plugins/ vendor plugins (install via Composer or download fresh per environment), node_modules/, vendor/, /wp-content/cache/.
4.4 Deployment workflow
Feature branch on dev's local. Code, commit, push to feature/* branch.
Open PR to staging. Review (self-review minimum; client-reviewed code is bonus).
Merge to staging. SSH to staging server, git pull, run composer install --no-dev, run npm run build, wp cache flush.
Client/editorial UAT on staging.
Once approved, open PR from staging to main. Merge.
SSH to production, git pull main, same install/build/flush sequence. Monitor for 30 min.

API keys never live in git or in the database. Use a .env file outside the web root, loaded via vlucas/phpdotenv from wp-config.php.

5.5 Three visual registers

In Phase 1 we implement Editorial fully, Dossier partially (the structural template), and Data Terminal in the Mission Control admin. The three registers share the token layer; switching is a CSS class on <html> that swaps overlay variables.

6.3 Implementation notes
The dashboard is registered via add_menu_page() in the AdminUI module, replacing the default index.php landing for editor and admin roles.
Widgets are individual partial templates in /plugins/ascendance-intelligence/templates/dashboard/widgets/.
Each widget loads its data via a REST endpoint (e.g. /wp-json/ascendance/v1/dashboard/subscribers), so the dashboard can update widgets without full page reloads.
Caching: each widget cached for 60 seconds in object cache (transients fallback if no Redis).
Permissions: editor role sees everything except API keys and DB-level details; admin role sees all.
Mobile-responsive: widgets stack vertically below 1024px viewport.
Uses the Data Terminal register tokens — dark navy background, mono numbers, red accents.

7.5 The 'tier' taxonomy and access control
Tier is a custom taxonomy, not a meta field. Three terms only: public, essential, professional. Set per-post via a sidebar meta box.
Access control runs server-side in the paywall enforcement filter (see Section 10). Non-public posts where the user lacks the tier never have their full content rendered to the browser — the gated portion is truncated server-side before being sent to the browser.
Never use display:none for paywall content
It's tempting to render full content and hide it with CSS. Don't. Anyone with DevTools can read it. Server-side truncation is the only acceptable pattern. Our paywall filter cuts the_content() output server-side based on tier check.

10.3 Stripe integration — the seven webhooks we handle
Stripe event
Our action
checkout.session.completed
First-time signup. Create the WP user if doesn't exist (matched by email), assign tier role, send welcome email, log to subscribers table.
customer.subscription.created
Defensive: ensures the subscription record is correct. Belt and braces with checkout.session.completed.
customer.subscription.updated
Tier change (upgrade/downgrade), period change. Update role and subscribers table.
customer.subscription.deleted
Cancellation took final effect. Demote role to standard 'subscriber' (so they can still log in but lose tier access). Send goodbye email.
invoice.paid
Successful renewal payment. Extend current_period_end. Log to activity log.
invoice.payment_failed
Failed renewal. Send 'card declined, please update' email. Mark subscriber as past_due. Stripe Smart Retries handle the retry schedule.
customer.subscription.trial_will_end
If trials are used. Send 'trial ending in 3 days' email. Phase 1 ships without trials but webhook is wired.
10.4 Webhook endpoint — minimum-viable implementation
<?php// /src/Stripe/WebhookController.phpnamespace Ascendance\Intelligence\Stripe;use Stripe\Webhook;use Stripe\Exception\SignatureVerificationException;class WebhookController{    public function register(): void    {        add_action('rest_api_init', function () {            register_rest_route('ascendance/v1', '/stripe/webhook', [                'methods'             => 'POST',                'callback'            => [$this, 'handle'],                'permission_callback' => '__return_true',  // signature verifies            ]);        });    }    public function handle(\WP_REST_Request $request)    {        $payload   = $request->get_body();        $signature = $request->get_header('stripe_signature');        $secret    = getenv('STRIPE_WEBHOOK_SECRET');        try {            $event = Webhook::constructEvent($payload, $signature, $secret);        } catch (\UnexpectedValueException $e) {            return new \WP_REST_Response(['error' => 'invalid payload'], 400);        } catch (SignatureVerificationException $e) {            return new \WP_REST_Response(['error' => 'invalid signature'], 400);        }        // Idempotency: skip if we've already processed this event id        if ($this->alreadyProcessed($event->id)) {            return new \WP_REST_Response(['ok' => true, 'skipped' => true], 200);        }        try {            match ($event->type) {                'checkout.session.completed'            => (new CheckoutCompletedHandler())->handle($event),                'customer.subscription.created'         => (new SubscriptionCreatedHandler())->handle($event),                'customer.subscription.updated'         => (new SubscriptionUpdatedHandler())->handle($event),                'customer.subscription.deleted'         => (new SubscriptionDeletedHandler())->handle($event),                'invoice.paid'                          => (new InvoicePaidHandler())->handle($event),                'invoice.payment_failed'                => (new PaymentFailedHandler())->handle($event),                'customer.subscription.trial_will_end'  => (new TrialEndingHandler())->handle($event),                default                                 => null,            };            $this->markProcessed($event->id);        } catch (\Throwable $e) {            error_log('Stripe webhook error: ' . $e->getMessage());            return new \WP_REST_Response(['error' => 'handler exception'], 500);        }        return new \WP_REST_Response(['ok' => true], 200);    }    /* alreadyProcessed() + markProcessed() write to a small idempotency table */}
Webhook idempotency is mandatory
Stripe retries webhooks. Without idempotency tracking, a retry creates duplicate subscriber records, double-sends welcome emails, double-logs activity. Always check 'have I seen this event_id before?' before doing any state change. The idempotency table can be tiny: event_id + processed_at, with a 7-day expiry.
10.5 Stripe Checkout — the signup flow
Phase 1 uses Stripe Checkout (hosted payment page) rather than building a custom payment form. Reasons: PCI scope stays out of our infrastructure, Stripe Tax works out of the box, and the UX is well-tested across hundreds of EU billing scenarios.
Visitor clicks 'Subscribe → Essential' on /subscribe/.
Our /wp-json/ascendance/v1/checkout/create endpoint creates a Stripe Checkout Session with the appropriate Price ID, success_url and cancel_url, customer_email (if logged in), and metadata['tier'].
Visitor redirects to Stripe-hosted Checkout. Enters card. Confirms.
Stripe redirects back to /membership-confirmation/?session_id=cs_...
Meanwhile (often before the redirect lands), Stripe fires checkout.session.completed webhook. Our handler creates the WP user, assigns tier role, sends welcome email, logs activity.
/membership-confirmation/ shows a thank-you and a 'Set your password' magic-link CTA. (We create the WP user with no password and send a one-time password-set link.)

11.2 The five-step editorial workflow
Step 1 — Input
Editor opens AI Studio. Selects article type (Brief / Update / Dossier), tier, topic, regions. Pastes raw notes, source URLs, press releases, or a structured outline. Optionally pastes 2–3 existing Briefs as voice reference. Selects AI provider (Claude default) and system prompt variant.
Step 2 — Generate
Click 'Generate draft'. Plugin sends request to the chosen API with: the system prompt, the editor's inputs, and (optionally) the voice-reference Briefs. Response streams back into the draft area in real time. Token count and cost update live.
Step 3 — Review and humanise
Editor reads the draft block-by-block. Can regenerate individual sections ('rewrite this paragraph more cautiously'), shorten, expand, or accept. Edits text directly. Fact-checks. Adds nuance. Removes anything that sounds AI-generated. This is the load-bearing step — the human's job is to make it indistinguishable from a hand-written Ascendance Brief.
Step 4 — Images
AI suggests image prompts and recommended dimensions. The editor sources / commissions / creates the actual image. (Phase 1 does NOT generate images — that's a Phase 2 decision once we've tested the workflow.)
Step 5 — Save to draft / send to editor
Editor saves to a standard WordPress draft. From here it goes through the normal publish workflow: tier assignment, schema verification, scheduling, publish. The AI Studio attaches metadata (ai_generated=true, ai_provider, ai_tokens_used) so we can track AI-assisted vs hand-written content over time.
11.3 System prompt — the editorial voice
The system prompt is the single most important configuration in the AI Studio. It encodes the Ascendance editorial voice: measured, institutional, evidence-led. It's stored in the database (wp_options) so the editorial team can refine it from the admin UI without involving a developer.

Direct HTTP integration via cURL or Guzzle. The Anthropic PHP SDK is also fine if the dev prefers.

11.5 OpenAI and Gemini equivalents
Each provider implements the same ProviderInterface. Switching is a dropdown in the AI Studio. Endpoints differ; the abstraction handles it.
OpenAI: https://api.openai.com/v1/chat/completions — model gpt-4-turbo or gpt-4o.
Gemini: https://generativelanguage.googleapis.com/v1beta/models/gemini-1.5-pro:generateContent — Google AI Studio API key.
All three return text + input/output token counts. We log all three to the ai_usage table with provider field set.

Every AI generation writes a row to wp_ascendance_ai_usage. The plugin enforces a monthly cap (default $100, configurable). If the running monthly cost exceeds the cap, the Generate button is disabled with an explanation. Admin can raise the cap from settings.

11.7 'Regenerate section' — the partial regenerate flow
Inside the AI Studio's draft view, each block (H2 section, paragraph) has a small toolbar: Regenerate, Shorten, Expand, More cautious. The editor highlights the block they want changed and clicks. We send the original block + the instruction + the surrounding context to the AI and replace just that block.
Implementation: each block is a contenteditable region with a data-block-id attribute. The toolbar action triggers a fetch to /wp-json/ascendance/v1/ai-studio/regenerate-section with the block content, instruction, and context. The response replaces the block.
11.8 Editorial transparency — the 'AI-assisted' badge
Every Brief drafted via AI Studio carries an ai_generated meta flag. Phase 1 does NOT display this on the public Brief (the human editor takes editorial responsibility). However, the Mission Control dashboard and the activity log track which content was AI-assisted so the team can monitor the mix and refine the workflow over time.
Editorial guideline (for the team)
Treat the AI Studio output as a first draft from a smart junior researcher. Useful structure, useful framing, useful first pass at evidence. Wrong on specifics often enough that everything needs verification. Names, dates, statistics, quotes — all require manual checking. The voice will need editing in roughly 30-40% of paragraphs to remove AI tells (over-balanced phrasing, unnecessary hedging, generic transitions). This is the human's job and what makes the workflow honest.

13.1 Yoast Free configuration
Site type: News / Magazine in the setup wizard.

14. AEO — Answer Engine Optimization
AEO is the discipline of being cited by AI answer engines: ChatGPT, Claude, Perplexity, Google AI Overviews. Different optimization targets from SEO — SEO targets clicks, AEO targets citations. For Ascendance, AI citations matter enormously: every cited mention reaches potential subscribers who would otherwise never find the firm.
14.1 The five AEO rules for every public Brief
Rule 1 — First paragraph is the citation paragraph
40–80 words. Self-contained. Fully answers the article title as a question. This is what the AI lifts verbatim.
Wrong: 'In May 2026, a quiet meeting in Lubumbashi reshaped the geometry of critical mineral supply chains…' (engages a reader; offers nothing to an AI).
Right: 'The US-DRC Strategic Partnership is a bilateral framework between the United States and the Democratic Republic of Congo, focused on critical minerals supply chains, infrastructure, and governance cooperation. Announced in 2022, it is now the principal counterweight to Chinese economic engagement in central Africa.'
Rule 2 — H2 headings phrased as questions
Structure articles with H2 headings as questions a reader (or an AI) might ask. 'What does the partnership cover?' beats 'Scope of the agreement'. This triggers FAQPage schema and is heavily favoured by AI answer engines.
Rule 3 — One claim per paragraph, evidence-led
State claim, then evidence, then implication. AI tools chunk text and lift paragraphs. Two claims in one paragraph either both lift (confusion) or both skip (loss).
Rule 4 — Name things first, define inline
Distinctive vocabulary you (Ascendance) coined, defined inline. 'The Strategic Asset Reserve framework — our methodology for assessing sovereign critical-mineral stockpiles — applies four tests: …' Every mention reinforces attribution.
Rule 5 — End with a Key Takeaways block
Above the fold: citable lead. Below the article: 3–5 bullet Key Takeaways. AI engines lift from both. The ACF block renders this consistently across all Briefs.

15. GEO — Generative Engine Optimization
GEO is about being the source AI models reach for at inference time, and being the source they cite in their answers. Related to AEO but with a longer time horizon. The mechanics aren't fully settled in mid-2026 — major LLM crawlers don't routinely fetch llms.txt yet, citation metrics are inconsistent, standards are emerging. But the cost to implement is low and being early is cheap insurance.
15.1 llms.txt — the proposed standard
llms.txt is a plain-text Markdown file at the site root giving AI tools a curated map. Our plugin auto-generates and maintains it.
Where it lives
https://ascendance-strategies.com/llms.txt — generated dynamically by our plugin's SeoFiles module, cached for 1 hour, regenerated whenever a public Brief publishes.
Generated format
# Ascendance Strategies> Ascendance Strategies is a Paris-based strategic intelligence advisory firm focused on the US-DRC Strategic Partnership, critical minerals supply chains, the Sakania-Lobito Corridor, and the Strategic Asset Reserve framework. llms.txt — honest framing
As of mid-2026, llms.txt is proposed but not ratified. Major LLM crawlers don't routinely fetch it. SEO-citation studies show no measurable improvement yet. We implement it as a half-day investment with optionality: if a major provider adopts it, we're ready. If not, we lose nothing.
15.2 robots.txt — the actually-effective lever
AI crawlers respect User-Agent rules in robots.txt. The Ascendance strategy is asymmetric:
Public Briefs: ALLOW major AI crawlers (GPTBot, ClaudeBot, PerplexityBot). Every citation builds brand authority.
Gated content: DISALLOW. AI crawlers should never index full subscriber content. Public excerpt is enough for citation.
CCBot (Common Crawl): DISALLOW entirely. CCBot is the corpus most LLMs train on. Allowing it means our content gets baked into model weights for free, with zero citation.
Generated robots.txt
Our plugin manages robots.txt dynamically via the robots_txt filter. Editable through plugin settings if rules need to change.

The paywall is the real defence
robots.txt is a request, not enforcement. A misbehaving crawler can ignore it. The actual defence against gated content being scraped is the server-side paywall in Section 10.6 — gated content never reaches the browser (or any bot) without an authenticated session. robots.txt is what we tell well-behaved crawlers; the paywall is what stops the others.
15.3 Semantic HTML — make it parseable
AI engines parse HTML structure. The custom theme uses:
HTML5 landmarks — <header>, <nav>, <main>, <article>, <aside>, <footer> — each once per page.
One H1 per page (the post title). H2 for major sections. H3 for sub-sections. No skipped levels.
Article body wrapped in <article>. Related links in <aside>.
<figure> + <figcaption> for images.
<blockquote cite='...'> for source quotes.
<time datetime='2026-05-22'> for dates.
Byline in <address> with rel='author'.
15.4 Topic clustering
Strongest GEO signal in 2026: be the most-linked source within a topic cluster.
Each top-level topic has a 'pillar page' — a long public-tier explainer Brief. Example: /intelligence/us-drc-strategic-partnership/.
Every Brief in that topic links back to the pillar page from its first paragraph.
The pillar page links out to every Brief and Update under it. Updated regularly.
Internal anchor text uses the pillar's exact title where natural.
Cross-topic links from cobalt-related Briefs to the Critical Minerals pillar AND the US-DRC pillar.

19. Security & Hardening
19.1 WordPress core hardening
WordPress core: latest stable. Minor auto-updates ON.
PHP 8.2 or 8.3. Confirm with OVH before launch.
Disable file editing in wp-admin: define('DISALLOW_FILE_EDIT', true);
Disable XML-RPC: add_filter('xmlrpc_enabled', '__return_false');
Move wp-config.php one directory above web root if hosting structure permits. Otherwise chmod 600.
Change database table prefix from wp_ to asc_ during install.
Force HTTPS site-wide. HSTS header with 1-year max-age.
Remove WordPress version from generator meta and from CSS/JS query strings.
19.2 Wordfence Free configuration
Firewall: ON. 'Learning Mode' for first week post-launch, then 'Enabled'.
Brute force protection: ON. Lockout after 5 failed logins, 4-hour lockout, permanent block at 20.
2FA: enforce for admin, editor. Required.
Strong password enforcement: ON for admin, editor, author.
Email alerts: to monitored mailbox. Critical only.
Live traffic: disable after initial calibration — heavy and rarely useful daily.
19.3 Login hardening
WPS Hide Login: move login to /login/. wp-login.php returns 404.
CAPTCHA on login and registration. Use hCaptcha (more EU-friendly than reCAPTCHA).
2FA enforced for admin/editor via Wordfence.
Password complexity: 12 chars min, mixed case + number + symbol.
Auto-logout after 24h inactivity for admin/editor sessions.
19.4 API key & secrets management
All keys in /home/ascendance/.env (outside web root, mode 600).
Loaded via vlucas/phpdotenv from wp-config.php.
Never in git, never in the database, never in PHP files inside the web root.
Use Stripe restricted keys where possible (PMPro replacement code can use restricted scope for most operations).
Rotate keys quarterly. Document the procedure in the handover.
19.5 Backup strategy — UpdraftPlus Free
Database: daily, retain 14 days.
Files: weekly, retain 4 weeks.
Destination: NOT the web server. OVH Object Storage, Backblaze B2 EU, or AWS S3 eu-west-3 (Paris).
Encryption at rest: enable in UpdraftPlus (free supports this).
Test restore monthly to staging. A backup never restored is not a backup.
19.6 Stripe and webhook security
Webhook signature verification on every event (see Section 10.4).
Idempotency table prevents duplicate processing.
Never log full webhook payloads to disk or to admin logs (contain customer PII).
Test mode on staging, Live mode on production. Visibly different keys to prevent mixed-mode bugs.
Pre-launch security scan
Three free scans, all mandatory before go-live: WPScan CLI, Wordfence Diagnostics, Mozilla Observatory (for HTTP headers). Address every High and Medium finding. Document the responses to each.

20.3 Subject Access Request workflow
GDPR Article 15 grants every subscriber the right to a copy of their data, and Article 17 the right to erasure. WordPress core has built-in tools.
WP-Admin → Tools → Export Personal Data — generates ZIP of everything WordPress knows.
WP-Admin → Tools → Erase Personal Data — anonymizes user record.
Our plugin registers data exporters and erasers via WordPress's privacy hooks — exports subscriber record, preference data, activity log.
SAR response SLA under GDPR: 30 days.
Document the workflow in the editor's manual: who handles requests, response template, escalation path.
20.4 Data minimization at registration
Collect only what's needed:
Email (required — login + communication)
First name + last name (required — invoices)
Organisation (optional — editorial segmentation)
Country (required — tax calculation, collected at Stripe Checkout)
Role / title (optional)
Marketing consent checkbox (unchecked default, explicit opt-in)
Do NOT collect: phone (unless Enterprise), date of birth, gender, full address (Stripe handles tax-address separately).

24.1 Phase 2 — Subscriber dashboard 2.0

24.2 Phase 3 — Entity profiles (scoped Sayari-style)
The original brief described Sayari-style entity-profile pages — named companies and people with structured profiles, relationships, linked records. Build a scoped version.
New CPT: entity (organisation, person, project, instrument).
Each entity gets a structured profile: identity, role, related entities, briefs mentioning, dossier appearances.
Linked records: when a tag matches an entity slug, the article auto-links.
Entity index page filterable by type.
Not a graph database — relationships stored as post meta with post-object references. Sufficient at Ascendance's scale.

Add-on storefront on /account/add-ons/.

Add-ons stack — base tier + multiple add-ons.
Billing handled as Stripe multi-item subscription.
24.4 Phase 5 — Client portal (gated documents area)

Watermark on PDF download with user identity.
Access log per document (who viewed, when).
Magic-link delivery (no need to log in).

The brief described a Data Terminal register for live ratings, charts, and ticker-style updates. Adds interactive data tools on top of the existing platform.

Schema scale (>20 interconnected data tables) hits Airtable/ACF limits.
The custom plugin built in Phase 1 is the migration foundation. Its data structures (subscribers, briefs, AI usage, schema, preferences) translate cleanly into Airtable tables or Postgres schemas. Phase 1 is not throwaway work — it's the foundation.
