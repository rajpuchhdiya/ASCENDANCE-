1. Project Overview & Scope
1.1 What we are building
Ascendance Strategies is a Paris-based advisory firm focused on the US-DRC Strategic Partnership (mining, energy, governance, security). They publish editorial intelligence on this market and want to convert their existing public website into a tiered subscription platform.
Phase 1 takes their existing WordPress site at ascendance-strategies.com and rebuilds it as a subscription-gated intelligence publication. Public visitors can read free articles and previews; paying subscribers in three tiers get access to the full archive and specific topic categories.
1.2 The three-user model
User type
What they can do
Public visitor
Reads free public articles in full.
Reads first 200–300 words (preview) of paywalled articles, then hits a 'Subscribe to continue' block.
Sees all article titles, deks, eyebrows, and category badges — discoverability stays high.
Can submit the newsletter signup form (free weekly digest of public articles).
Subscriber
Authenticated via WordPress login (email + password; Phase 2 adds magic link).
Tier-based content access (Essential / Professional / Enterprise).
Receives weekly digest plus per-category notifications for new articles in their tier.
Account page: manage billing, change tier, cancel, update payment method (Stripe Customer Portal).
Personal dashboard: latest articles in their tier, recently published, saved articles (Phase 2).
Editorial / admin
Logs in to WordPress admin (wp-admin) with Editor or Administrator role.
Drafts content using the standard WordPress block editor. AI generation is NOT in scope for Phase 1 — added in Phase 2 / Option B upgrade.
Tags articles with categories, sets tier visibility, schedules publication.
Reviews and approves subscriber registrations if manual approval is required (configurable).
1.3 What is in scope for Phase 1 (this build)
Complete website rebuild on a new custom WordPress theme, brand-token-based.
Three-tier subscription system with Stripe billing, EU VAT handling, customer portal.
Paywall and tier-gating on intelligence content with public preview snippets.
Custom post types: Intelligence Brief, Update, Dossier.
Sample category taxonomy aligned with US-DRC focus (see Section 15).
Public surfaces: Home, About, Services, Industries, Intelligence (article archive), FAQ, Events, Contact, Newsletter, Privacy, Terms.
Subscriber surfaces: Login, Register, Pricing, Account, Dashboard, Tier-upgrade flow.
Full SEO foundation (Rank Math Pro, schema, sitemaps, structured data).
AEO baseline (Q&A formatting, FAQ schema, E-E-A-T markup).
GEO baseline (llms.txt, AI crawler robots.txt, citable content patterns).
Newsletter integration (Loops, Mailchimp, or Brevo — to be confirmed with client at kickoff).
Search (WordPress core + SearchWP).
Analytics (GA4 + Search Console + conversion events).
Migration of existing content with URL preservation (301 redirects where structure changes).
Hosting on existing OVH infrastructure with staging + production environments.
Training videos (see Section 20) and handover documentation.
30 days post-launch bug-fix support.
1.4 What is NOT in scope for Phase 1
Explicitly deferred to Phase 2 / future engagement
AI-assisted article generation (Claude / GPT / Gemini API integration in the admin).
Sayari-style entity profile pages with cross-referenced relationships.
Custom client portal (secure document area for advisory clients).
Watchlists, ratings, interactive data tools.
Three distinct visual registers — Phase 1 uses the Editorial register only.
Algolia / Typesense — WordPress + SearchWP only for Phase 1.
Cross-domain SSO with a separate Next.js platform.
Native mobile app (mobile-responsive web only).
Multi-language site beyond existing English + French.
If during the build the client requests anything in the list above, raise a change order — do not silently absorb it.

2.3 Environments
Three environments, all on OVH:
Local. Each developer's machine, using Local by Flywheel, LocalWP, or DDEV. Mirror PHP/MySQL versions to production.
Staging. On the OVH plan or a subdomain like staging.ascendance-strategies.com. Password-protected at the server level (HTTP Basic Auth) so search engines do not index it. Stripe in test mode. All emails routed to a single test inbox.

2.4 Credentials & secrets
Store nothing sensitive in source code or the wp_options table in plain text. Use:
WordPress wp-config.php constants for the most critical secrets (DB credentials, Stripe API keys, SMTP credentials).
Environment variables via a .env file (loaded with vlucas/phpdotenv) for non-WordPress-core secrets.
A shared password manager (1Password / Bitwarden) for the team. Never send keys over email or Slack.

3.5 Tone & registers
The brand commits to three visual registers: Editorial, Data Terminal, and Dossier. Phase 1 builds Editorial only. The token system must accommodate the other two so they can be added in Phase 2 by adding new tokens, not rewriting components.
Editorial (Phase 1)
Background: --color-cream. Serif-led typography. Articles, homepage, public reading surfaces. The default for Phase 1.
Data Terminal (Phase 2)
Background: --color-navy-deep. Mono-heavy, dense data presentation. Trackers, ratings, dashboards. Deferred but build tokens so component CSS handles dark backgrounds without rewrites.
Dossier (Phase 2)
Background: --color-white. Long-form living documents with embedded data blocks. Subscriber-only.
To support this, write component CSS using semantic tokens like --surface-bg, --surface-text, --surface-border. Map those to the concrete color tokens per register. Switching register = swapping the mapping, not rewriting components.
/* Semantic surface tokens — one register active at a time *//* default: editorial register */:root {  --surface-bg: var(--color-cream);  --surface-card: var(--color-white);  --surface-text: var(--color-text-primary);  --surface-text-muted: var(--color-text-muted);  --surface-border: var(--color-divider-light);  --surface-accent: var(--color-red);}/* Phase 2 — data terminal register */[data-register="terminal"] {  --surface-bg: var(--color-navy-deep);  --surface-card: var(--color-navy-mid);  --surface-text: var(--color-cream);  --surface-text-muted: #B0B0BD;  --surface-border: var(--color-divider-dark);  --surface-accent: var(--color-red-light);}

4.2 URL conventions
Lowercase, hyphen-separated. No underscores, no capitals.
No trailing slug noise (avoid /intelligence/article-2026-05-22-mining-sector-update/; use /intelligence/mining-sector-update/).
Category in URL only on category archive, not on the single post slug. (/intelligence/{slug}/, not /intelligence/{category}/{slug}/.) This keeps URLs short and lets us re-categorise without breaking links.
No dates in URLs. Briefs are evergreen reference material; a 2024 brief stays useful in 2027.
French translations live at /fr/{slug}/ with hreflang annotation.

4.5 Redirects (existing → new)
Audit the existing ascendance-strategies.com sitemap before launch. For every URL that changes:
Add a 301 redirect from old → new in WP Rocket or via Rank Math's Redirections module.
Test every redirect with curl -I before launch.
Submit the new sitemap to Google Search Console on launch day.
URL preservation matters
Existing SEO equity lives at existing URLs. Every URL we change without a 301 redirect costs ranking. Test redirects on staging before launch — do not 'fix it after we go live'.

5. Custom Post Types & Taxonomies
All long-form intelligence content lives in three custom post types. Standard WordPress Posts are reserved for the public-facing editorial section (news, opinion, lighter content). This separation matters because it lets us apply different templates, different paywall rules, different schema markup, and different archive logic per content type.
5.1 The three intelligence post types
CPT slug
Label
Purpose
brief
Intelligence Brief
The flagship format. 1,500–3,000 word analytical pieces on a named topic. Each has a clear analytical claim, evidence, and citations. Most are subscriber-gated; some teaser briefs are public to drive subscriptions and AI citations.
update
Update
Short-form (300–800 words) developments on an existing topic. Time-sensitive. Always dated. Always references the parent Brief(s) they update.
dossier
Dossier
Long living documents (3,000+ words) on a major topic. Versioned. Updated rather than replaced. Highest tier only. Includes embedded data blocks.

5.2 Registration (PHP)
Register all three CPTs from the custom theme's functions.php (or better, from a small mu-plugin so they survive a theme change). The example below registers brief; mirror the pattern for update and dossier.
<?php// /wp-content/mu-plugins/ascendance-cpts.phpadd_action( 'init', 'ascendance_register_brief_cpt' );function ascendance_register_brief_cpt() {    register_post_type( 'brief', array(        'labels' => array(            'name'               => 'Intelligence Briefs',            'singular_name'      => 'Brief',            'add_new_item'       => 'Add New Brief',            'edit_item'          => 'Edit Brief',            'menu_name'          => 'Briefs',        ),        'public'              => true,        'has_archive'         => 'intelligence',        'rewrite'             => array( 'slug' => 'intelligence', 'with_front' => false ),        'supports'            => array( 'title', 'editor', 'excerpt', 'thumbnail', 'author', 'revisions', 'custom-fields' ),        'show_in_rest'        => true,        'menu_icon'           => 'dashicons-analytics',        'menu_position'       => 5,        'taxonomies'          => array( 'topic', 'region', 'tier' ),    ) );}
Why mu-plugins, not the theme
CPTs registered in the theme disappear if the theme is switched. Disappearing CPTs do not mean the posts vanish — they become orphans, invisible in the admin until the CPT is re-registered. Always register CPTs in a must-use plugin (/wp-content/mu-plugins/).
5.3 Taxonomies
Four custom taxonomies handle our content organization. Do not use WordPress's default 'category' or 'post_tag' on the intelligence CPTs — they are reserved for the editorial Posts.
Taxonomy
Hierarchical?
Purpose & examples
topic
Yes
The primary editorial classification. Hierarchical so we can nest (e.g. Critical Minerals > Cobalt). Examples: US-DRC Partnership, Critical Minerals, Sakania-Lobito Corridor, Strategic Asset Reserve, Energy & Infrastructure, Governance.

5.4 ACF Pro field groups
Each CPT gets an ACF Pro field group with these fields. Do not store this in the database via wp_options — keep field definitions exportable as PHP via ACF's Local JSON or PHP export, so they live in version control.
Field group: Intelligence Brief
Subhead / dek (text, single line) — the italic subtitle below the headline.
Analytical claim (textarea, 1–2 sentences) — the brief's thesis in one sentence. Required.
Public excerpt (textarea, 50–80 words) — visible to non-subscribers when the brief is gated. This is the AI-citation surface. Required.
Key takeaways (repeater, 3–5 items, each one bullet line) — appears as a callout block at the top.
Sources (repeater, each with: source name, URL, date) — the brief's evidence base. Renders as a 'Sources' section at the bottom.
Related briefs (post object, multiple, query CPT=brief) — three to five linked briefs.
Brief version (number, default 1) — incremented when the brief is substantively revised. Updates do not increment.
Field group: Update
Update for (post object, single, query CPT=brief or dossier) — the parent brief this updates. Required.
Update date (date picker) — when the development happened, not when published. Required.
One-line summary (text, single line, max 160 chars) — also used as the meta description.
Field group: Dossier
All Brief fields, plus:
Last revised (date picker, auto-updated on save).
Revision log (repeater: date + summary of change).
Data blocks (repeater: block title + structured data table) — for embedded data sections.
Companion downloads (file repeater) — PDFs of the dossier at major revision points.
ACF JSON sync
Enable ACF Pro Local JSON by creating /wp-content/themes/ascendance/acf-json/. Every field group save writes a JSON file there; on a fresh environment, ACF reads from JSON on activation. This is how field groups travel through git from local → staging → production.

10. AEO — Answer Engine Optimization
AEO is the discipline of being cited by AI-powered answer engines: ChatGPT, Claude, Perplexity, Google AI Overviews, You.com. It is related to SEO but the optimization targets are different. SEO targets clicks. AEO targets citations — the AI quotes you in its answer, ideally with attribution and a link.
For a niche subscription publisher, AEO is especially valuable: every AI citation that names Ascendance creates brand recognition with the exact audience that would subscribe. The free public Briefs are the citation surface; the gated Briefs are the conversion surface.
10.1 The five AEO rules for every public-tier piece
Rule 1 — The first paragraph is the citation paragraph
Open with a 40–80 word paragraph that fully answers the article's title as a question, in a single self-contained block. This is what the AI will lift verbatim. Do not bury the answer; do not start with a scene-setter or anecdote.
Wrong: 'In May 2026, a quiet meeting in Lubumbashi reshaped the geometry of critical mineral supply chains in central Africa…' (Reader is engaged; AI cannot summarise.)
Right: 'The US-DRC Strategic Partnership is a bilateral framework between the United States and the Democratic Republic of Congo, focused on critical minerals supply chains, infrastructure, and governance cooperation. Announced in 2022, it is now the principal counterweight to Chinese economic engagement in central Africa.' (Self-contained, factual, citable.)
Rule 2 — Use explicit question headings
Structure articles with H2 headings phrased as questions a reader (or an AI) might actually ask. 'What does the partnership cover?' beats 'Scope of the agreement'. The H2-as-question pattern is what triggers FAQPage schema and is heavily favoured by AI answer engines.
Rule 3 — One claim per paragraph, evidence-led
Each paragraph: state a claim, then evidence, then implication. Avoid running multiple claims into a single paragraph — AI tools chunk text and lift paragraphs, so two claims in one paragraph either both get lifted (loss of clarity) or both get skipped (loss of citation).
Rule 4 — Name things first, define them inline
Use distinctive vocabulary that you (Ascendance) coined, and define it inline. 'The Strategic Asset Reserve framework — our methodology for assessing sovereign critical-mineral stockpiles — applies four tests: …'. If the AI is going to cite the concept, it will cite your name for it. This is the strongest GEO lever: become the source of the vocabulary.
Rule 5 — End with a TL;DR or 'Key takeaways' block
Above the fold: the citable lead paragraph. Below the article: a 3–5 bullet 'Key takeaways' block. AI engines lift from both. The ACF 'Key takeaways' field renders this block consistently across all Briefs.
10.2 FAQPage schema — example
For any post with H2 questions, mark up FAQPage schema. Rank Math Pro does this through its FAQ block; the dev should ensure the block is enabled and editors are trained to use it.

10.4 Citation-friendly phrasing
Use short, declarative sentences. 'X is Y.' AI engines prefer these to compound sentences.
Use precise dates, not relative time. 'In May 2026' beats 'recently'.
Name actors explicitly every time, do not rely on pronouns. 'The AFC-led consortium' beats 'they' in any context an AI might lift.
Avoid headline-style ambiguity in body text. The article body should be unambiguous prose; clever headlines are fine.
Quote your own framework names. 'Under our Strategic Asset Reserve framework, …' — every time you mention the framework, you reinforce attribution.

11. GEO — Generative Engine Optimization
GEO sits next to AEO but covers a slightly different problem. AEO asks: when an AI search engine answers a question, does it cite us? GEO asks: when a generative model writes about our topic, does our content shape its answer? GEO is about being the source the model learned from, and being the source it reaches for at inference time.
Honest framing: GEO in mid-2026 is a hedge. The mechanics aren't fully settled, the AI providers don't yet agree on standards, and measurable ROI is rare. But the cost to implement is low, and being early is cheap insurance. We will ship the full GEO stack in Phase 1.
11.1 llms.txt — the proposed standard
llms.txt is a plain-text Markdown file at the site root that gives AI tools a curated map of the site. As of mid-2026, llms.txt is still a proposal, not a ratified web standard. Major LLM crawlers do not yet routinely fetch it. But IDE agents, dev tools, and some niche AI search products do, and the cost to ship one is half a day.
Ship it. Treat it as zero-yield insurance.

11.2 robots.txt — the actually-effective lever
robots.txt is where the real control lives. AI crawlers (GPTBot, ClaudeBot, PerplexityBot, Google-Extended, CCBot) respect User-Agent-specific rules. The strategy for Ascendance is asymmetric:
Public content: ALLOW major AI crawlers. We want our public briefs cited by AI engines because every citation builds brand authority among potential subscribers.
Gated content: DISALLOW. AI crawlers must never index full subscriber content. They can cite the public excerpt and the headline; the rest is paid.
Common Crawl (CCBot): DISALLOW entirely. CCBot is the corpus most LLMs train on. Allowing CCBot means our content gets baked into model weights for free, with no citation. That is the worst possible trade.

The paywall is the real defence
robots.txt is a request, not an enforcement. A misbehaving crawler can ignore it. The actual defence against gated content being scraped is the server-side paywall: gated content is never sent to a browser (or a bot) without an authenticated session. robots.txt is what we tell well-behaved crawlers to do; PMPro is what prevents misbehaving ones from succeeding.
11.3 Semantic HTML — make it parseable
AI engines parse HTML structure to understand content. Sloppy markup (div soup, inconsistent heading levels, missing landmarks) makes content harder to chunk and cite. The custom theme must use:
Proper HTML5 landmarks: <header>, <nav>, <main>, <article>, <aside>, <footer>. Each used once per page in the conventional way.
One H1 per page, matching the post title. H2s for major sections. H3s for sub-sections. Never skip a level.
Article body wrapped in <article>. Sidebar in <aside>. Related articles block in <aside>.
<figure> and <figcaption> for images with captions.
<blockquote cite="…"> for source quotes.
<time datetime="2026-05-22"> for dates.
Author byline wrapped in <address> with rel="author" link.
11.4 Citable content patterns
Building on the AEO rules in Section 10, these additional patterns help LLMs lift content cleanly:
Definitional sentences in the opening — 'X is Y' format.
Numbered lists for multi-step explanations. Bulleted lists for parallel-structure enumerations. Both are easy for LLMs to lift.
Comparison tables — 'How X differs from Y' tables get cited disproportionately.
Explicit framework attribution — 'In Ascendance's Strategic Asset Reserve framework, the four tests are: …' (every mention reinforces attribution).
Distinct quotable lines — at least one sentence per Brief that is concise, claim-shaped, and includes the firm's analytical voice. These get pulled as pull-quotes by AI engines.
11.5 Topic clustering
Cluster all content within a topic into a tight internal-link graph. Strongest GEO signal in 2026 is being the most-linked source within a topic cluster.
Each top-level topic has a 'pillar page' — a long evergreen explainer (Brief, public tier). Example: '/intelligence/us-drc-strategic-partnership/'.
Every Brief in that topic links back to the pillar page from its first paragraph.
The pillar page links out to every Brief and Update under it. Updated regularly.
Internal anchor text uses the pillar's exact title where natural — 'As we explained in our brief on the US-DRC Strategic Partnership…'
Cross-topic links are less common but valuable. A Brief on cobalt should link to both the Critical Minerals pillar and the US-DRC pillar.

15. Security & Hardening
Security work is plumbing — invisible when done right, catastrophic when skipped. The list below is non-negotiable for Phase 1 launch.
15.1 WordPress core hardening
WordPress core: latest stable. Auto-update minor versions; manual review for major releases.
PHP 8.2 or higher. PHP 8.1 reached end of life; PHP 8.0 is unsupported. Confirm with OVH.
Disable file editing in wp-admin: add `define( 'DISALLOW_FILE_EDIT', true );` to wp-config.php.
Disable XML-RPC unless explicitly needed: filter with `add_filter('xmlrpc_enabled', '__return_false');`.
Move wp-config.php one directory above the web root (OVH structure permitting), or restrict its permissions to 600.
Database table prefix: change from default `wp_` to something like `asc_` during install.
Force HTTPS: redirect all HTTP to HTTPS at the OVH / Nginx level. HSTS header with 1-year max-age.
Remove WordPress version from generator meta tag and from CSS/JS file query strings.
15.2 Wordfence configuration
Wordfence Free is sufficient for Phase 1; Premium upgrade later if attack volume warrants.
Firewall: enable. Run in 'Learning Mode' for one week post-launch, then switch to 'Enabled'.
Brute force protection: ON. Lockout after 5 failed logins. Lockout duration: 4 hours. Block forever if 20+ failures.
Two-factor authentication: enforce for all admin and editor roles. Required.
Strong password enforcement: ON for admin, editor, author.
Email alerts: to a monitored mailbox. Critical issues only (not every benign scan).
Live traffic / scans: enable initially, disable after launch — these are heavy and you don't need them daily once the site is stable.
15.3 Login security
Move login to /login/ via WPS Hide Login. wp-login.php returns 404.
CAPTCHA on login and registration. Use hCaptcha (more EU-friendly than reCAPTCHA).
Force 2FA for all admin / editor accounts via Wordfence or WP 2FA plugin.
Password complexity: 12 characters minimum, mixed case + number + symbol.
Auto-logout after 24 hours of inactivity for admin / editor sessions.
Limit login attempts per IP (Wordfence handles this).
15.4 API key & secrets management
API keys (Stripe, Brevo, Anthropic in Phase 2) must never live in the database or in plain-text config files inside the web root.
Define keys in wp-config.php as constants: `define('STRIPE_SECRET_KEY', '...');`.
Better: load from environment variables. Use a .env file outside the web root, read via a small bootstrap in wp-config.php (e.g. vlucas/phpdotenv).
Never commit wp-config.php or .env to git. Add to .gitignore on day one.
Rotate keys quarterly. Document the rotation procedure for the client.
Use Stripe restricted keys where possible (PMPro mostly needs the full secret, but custom integrations should use restricted).
15.5 Backup strategy
UpdraftPlus (free tier sufficient for Phase 1) handles automated backups.
Database: backed up daily. Retain 14 days.
Files (uploads, themes, plugins): backed up weekly. Retain 4 weeks.
Backup destination: NOT the web server. Use OVH Object Storage, AWS S3 (eu-west-3 Paris), or Backblaze B2 (EU).
Encrypt backups at rest. UpdraftPlus has an encryption option — use it.
Test restore monthly. A backup you have never restored is not a backup.
15.6 PMPro and Stripe-specific security
PMPro webhook endpoint: protected by Stripe signature verification (PMPro handles this if configured correctly).
Test the webhook endpoint with Stripe CLI before launch; verify rejected payloads with invalid signatures.
Never log full webhook payloads to disk or to admin logs (they contain customer PII).
Stripe Test mode on staging, Live mode on production. Use clearly different keys; many bugs come from mixed-mode environments.
PMPro 'Member Actions' email alerts: enable for cancellations and refunds (the client wants to know quickly).
Penetration test before launch?
A formal pentest is overkill for Phase 1 budget. But running the site through three free scanners is mandatory: WPScan (CLI), Wordfence's Diagnostics, and Mozilla Observatory (for headers). Address every High and Medium finding before go-live.

Premium subscribers pay extra to unlock additional categories beyond their tier. Implemented via PMPro Variable Pricing or custom payment intent flow with Stripe.
Add-on storefront on /account/add-ons/.
Each add-on: monthly or annual price, single category access (e.g. unlock 'Energy' as an Essential subscriber).
Add-ons stack: a subscriber can hold base tier + 3 category add-ons.
Billing handled by Stripe Subscriptions with multiple items.
21.5 Phase 2.5 — Client portal (gated documents area)
The brief mentions an advisory-client portal — secure document and report access. Phase 2.5 builds the basic version.
New CPT: client_doc (private, never publicly listed).
Per-document access control — only specific user(s) can see each document.
Watermark on download (PDF processing via TCPDF or similar).
Access log per document (who viewed when).
Magic-link delivery (no need for client to log in).
21.6 Phase 3 — When to migrate off WordPress
WordPress will serve Ascendance well for the first 12–18 months. Migration to the full Next.js + Airtable + Clerk architecture in the original brief (Option C) makes sense when one of these triggers fires:
Subscriber count exceeds 500 — performance and tier-gating complexity outgrow WordPress.
Interactive data tools needed (live ratings, real-time dashboards, charting).
Genuine cross-subdomain SSO required (subscriber product on a separate platform.* subdomain).
Native mobile app required.
Schema scale (>20 interconnected data tables) hits Airtable / Custom Fields limits.
At that point, the custom plugin built in Phase 2.1 onwards is the migration foundation: the data structures translate directly into Airtable tables or Postgres schemas. Phase 1 + Phase 2 is not throwaway work — it is the foundation.
